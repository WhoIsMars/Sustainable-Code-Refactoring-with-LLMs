### Contesto Estratto: Progetto di Tesi (Analisi Codice LLM)

#### 1. 🎯 Obiettivo Principale del Progetto

Il progetto è una tesi di ricerca sperimentale focalizzata sul **refactoring automatico del codice** tramite Large Language Models (LLM). L'obiettivo primario è valutare se, quanto e come diversi LLM (specificamente **OpenAI, Gemini, Claude**) riescano a migliorare le **prestazioni e la sostenibilità computazionale** di snippet di codice reali, confrontandoli con le versioni "base" scritte da umani.

#### 2. 📂 Dataset e Struttura dei Dati

Il dataset è organizzato in "cluster", dove ogni cluster raggruppa codici relativi allo stesso esercizio (spesso da Exercism).

* **Entità di Base (Base Code):** Snippet di codice sorgente (in linguaggi come C, C++, Go, Java, Python, JS, TS) ottenuti da repository GitHub.
* **Entità LLM (LLM Code):** Per ogni "base code", sono state generate **12 varianti**: una per ciascuno dei 3 modelli LLM, utilizzando 4 versioni distinte di prompt (v1, v2, v3, v4).
* **File di Metadati (Cluster):** I metadati di ogni cluster (che descrivono le entry, i loro path, ecc.) sono salvati in file JSON dedicati, come `src/clusters/cluster_bob.json`.

#### 3. ⚙️ Pipeline di Esecuzione e Metriche

Per valutare le performance, ogni singolo snippet di codice (sia base che LLM) viene eseguito e testato.

* **Esecuzione dei Test:** Ogni snippet ha una test suite associata. L'esecuzione avviene in ambienti isolati tramite **Docker/Colima**, orchestrati dallo script `src/run_tests_on_clusters/run_tests_on_cluster.py`.
* **Significatività Statistica:** Per garantire robustezza, ogni file (base e LLM) viene testato **5 volte**.
* **Metriche Raccolte (Grezze):** Per ogni esecuzione vengono misurate:
    * `CPU_usage`
    * `RAM_usage`
    * `execution_time_ms`
    * `regressionTestPassed` (che per gli LLM diventa un "pass rate")
* **Metriche Derivate (Green Computing):** Vengono inoltre calcolate metriche di sostenibilità:
    * **Consumo Energetico (Joules):** Calcolato stimando la potenza (Watt) da `CPU_usage` (basata sul TDP del processore) e `RAM_usage` (consumo per GB), moltiplicata per il tempo di esecuzione e un fattore PUE (Power Usage Effectiveness).
    * **Impronta di Carbonio (gCO2eq):** Ottenuta convertendo i Joules in kWh e applicando un fattore di intensità di carbonio specifico (es. gCO2eq/kWh).
* **File di Output (Risultati):** I risultati delle 5 esecuzioni sono salvati in `src/execution_outputs/`. La nomenclatura è stringente:
    * **Base Code:** `{clusterName}_results_{executionNumber}.json` (es. `bob_results_4.json`).
    * **LLM Code:** `{clusterName}_results_v{promptVersion}_{executionNumber}.json` (es. `bob_results_v1_3.json`).

#### 4. 📊 Analisi Statistica e Calcoli Chiave

L'analisi si basa sul confronto tra le metriche del codice base e quelle del codice LLM.

* **Unità Statistica:** Per ogni calcolo, l'unità di misura non è la singola esecuzione, ma la **media delle 5 esecuzioni** relative a uno specifico snippet.
* **Filtro Metodologico:** Un punto chiave è che l'analisi delle performance e della sostenibilità per gli snippet LLM viene eseguita **solo sulle entry che hanno superato il 100% dei test di regressione**, per misurare l'efficienza solo del codice *corretto*.
* **Calcolo dell'Improvement %:** La metrica fondamentale per il confronto è l'improvement percentuale, calcolato *entry per entry* come:
    `Improvement % = ( (media_5_esec_LLM - media_5_esec_base_code) / media_5_esec_base_code ) * 100`.
* **Interpretazione dell'Improvement:**
    * Per `CPU_usage`, `RAM_usage`, `execution_time_ms`, **`Energy_Joules`** e **`Carbon_gCO2eq`**: un valore **negativo** indica un *miglioramento* (riduzione del consumo/impatto).
    * Per `regressionTestPassed` (Pass Rate): un valore **negativo** indica un *peggioramento* (meno test superati).

#### 5. 🔬 Obiettivi Scientifici Secondari

Oltre alla performance pura, la tesi indaga il "come" e il "perché" dei cambiamenti:

1.  **Valutazione della Sostenibilità (Green Computing):** Analizzare se i refactoring degli LLM portano a una riduzione misurabile del consumo energetico (Joules) e dell'impronta di carbonio (gCO2eq), correlando i risparmi ai modelli, ai prompt e ai linguaggi.
2.  **Analisi di Similarità:** Correlare i miglioramenti di performance con metriche di similarità (es. cosine similarity, fuzzy) per capire se i codici molto diversi performano meglio/peggio.
3.  **Identificazione di Pattern:** Isolare un sottoinsieme di snippet con (Bassa Similarità + Alto Improvement). Su questi, eseguire analisi (AST, regex) per identificare **pattern di refactoring ricorrenti** introdotti dagli LLM e correlare la presenza di un pattern a un miglioramento misurabile.

#### 6. 🛠️ Struttura dei Moduli e Strumenti Chiave

Il progetto è strutturato in una codebase Python modulare:

* **`src/utility_dir/`:** Contiene `utility_paths.py` per la gestione centralizzata dei percorsi e `general_utils.py` per funzioni comuni (es. `read_json`, `write_json`, `get_cluster_names`).
* **`src/run_tests_on_clusters/`:** Nucleo dell'esecuzione dei test e della raccolta metriche.
* **`src/metrics/`:** Suite di script per l'analisi statistica. Include moduli specifici per:
    * `energy/energy_analyzer.py`: Calcolo delle metriche energetiche e di carbonio.
    * `patterns/`: Analisi dei pattern di codice.
    * `similarity/`: Calcolo della similarità tra snippet.
* **`src/unified_analyzer/`:** Un modulo consolidato che gestisce la **validazione dei dati**, il rilevamento di anomalie (outlier, valori mancanti/invalidi) e la **Root Cause Analysis** degli errori di esecuzione.
* **`src/pipeline.py`:** Un modulo orchestratore che automatizza il workflow completo: 1. Analisi Errori (`unified_analyzer`) -> 2. Riesecuzione Mirata dei fallimenti -> 3. Ricalcolo Statistiche (`metrics`).
* **`src/main.py`:** Entry point principale del progetto, implementato come una TUI (Text-based User Interface) "grafica" (basata su `rich`) per orchestrare le varie fasi (Esecuzione, Analisi, Pipeline).
